# AGENTS.md — инструкции для ИИ-агента, разрабатывающего сайт MATRITSA

Этот файл агент читает первым, перед началом любой работы над проектом. Здесь — то, что
агент не может угадать сам. Подробный функционал — в `SPEC.md`, визуальные токены — в `DESIGN.md`.

## 1. Структура и стек (Structure & Stack) — зафиксировано, не менять без согласования

- **Фреймворк:** Next.js (App Router), TypeScript
- **Стилизация:** Tailwind CSS — все цвета/отступы только через токены из `DESIGN.md`
  (настроить в `tailwind.config` как именованные значения, а не хардкодить hex/px в JSX)
- **CMS:** Sanity (headless) — для контента, который заказчик должен редактировать сам:
  тексты услуг, фото, цены/товары каталога, отзывы, портфолио. Sanity Studio — облачная
  (studio.sanity.io), отдельно от VPS — это снимает с сервера нагрузку по хостингу админки
  и упрощает деплой (см. раздел «Хостинг» ниже)
- **Хостинг:** VPS на Рег.облаке (reg.ru), регион размещения — Москва/Московская область.
  Next.js разворачивается в режиме сервера (`next build && next start`, НЕ статический
  экспорт — нужен SSR/API-роуты для форм), под управлением process-менеджера (pm2 или
  systemd unit), за Nginx как reverse proxy, с TLS через Let's Encrypt/Certbot. Деплой —
  через git pull + build на сервере или CI (GitHub Actions → SSH деплой) — способ зафиксировать
  в README после реализации.
- **Формы:** API-роут в Next.js → отправка уведомления в Telegram (бот) владельцу +
  сохранение заявки (в Sanity как документ типа `lead`, либо в отдельную БД — на выбор агента,
  главное чтобы ничего не терялось молча при ошибке отправки в Telegram)
- **Аналитика:** Яндекс.Метрика с целями на каждой из 4 посадочных страниц (клик по CTA,
  отправка формы, клик по мессенджеру) — см. `SPEC.md` раздел SEO/аналитика
- **Регион бизнеса (для локального SEO и Яндекс.Директа):** Москва и Московская область
- **Язык интерфейса и контента:** русский

## 2. Ограничения (Constraints)

### Всегда
- Использовать только именованные токены дизайна из `DESIGN.md` (`bg`, `surface`, `accent`,
  `accent-secondary`, `metal`, `text-primary`) — никаких произвольных hex/px в коде
- Семантическая HTML-разметка (правильные теги `header`, `nav`, `main`, `section`, `footer`,
  один `h1` на страницу)
- Alt-текст у каждого изображения
- Адаптивная вёрстка — проверять минимум на 375px (мобильный), 768px (планшет), 1440px (десктоп)
- У каждой из 4 посадочных страниц (Главная, Компьютерная помощь, 3D-печать, Инженерные
  разработки) — собственные уникальные `<title>`, `<meta description>`, `<h1>` и Schema.org
  разметка (см. `SPEC.md`)
- Контраст текста к фону — не хуже WCAG AA (учитывая, что фон тёмный `#0D1117`)
- Реальный текст из `SPEC.md` вставлять как есть — не заменять на свои формулировки и не
  генерировать вместо него плейсхолдеры вида "Lorem ipsum" или "Заголовок страницы"
- Изображения для мест, помеченных в `SPEC.md` как "генерировать" — генерировать по указанным
  промптам через доступный инструмент генерации изображений, единым визуальным стилем
  (см. `SPEC.md` раздел «Изображения»)
- Настроить сервер в безопасной конфигурации: firewall (ufw/iptables) с открытыми только
  80/443/22 (SSH желательно на нестандартном порту или по ключу без пароля), автообновления
  безопасности ОС, TLS обязателен (без http без редиректа на https)

### Спросить, прежде чем делать (ask-first)
- Добавление любой новой зависимости, не упомянутой в этом файле
- Изменение цветовой палитры или структуры страниц, зафиксированной в `SPEC.md`
- Любое отклонение от указанного стека (например, желание использовать другой хостинг/CMS)

### Никогда
- Не хардкодить цвета/отступы в коде вместо токенов
- Не использовать Inter, Arial, Roboto или системный шрифт по умолчанию (см. `DESIGN.md`)
- Не коммитить секреты/API-ключи в репозиторий (использовать `.env` на сервере, добавить
  в `.gitignore`)
- Не публиковать сайт без хотя бы одного реального прогона форм заявки (см. критерии приёмки)
- Не оставлять на боевых страницах placeholder-контент («текст здесь», «фото скоро» и т.п.)
- Не хранить пароли/ключи доступа к VPS в коде или в чатах — только в защищённом хранилище
  секретов (менеджер паролей, переменные окружения CI)

## 3. Порядок работы (Phases)

Работать по фазам из `SPEC.md` раздел «Фазы разработки» — небольшими проверяемыми шагами,
не пытаться сделать весь сайт одним проходом. После каждой фазы — самопроверка по критериям
приёмки этой фазы (checklist в `SPEC.md`) прежде чем переходить к следующей.

## 4. Как агент должен проверять свою работу (Verification)

Перед тем как считать фазу/сайт готовым:
1. `npm run build` — сборка проходит без ошибок и предупреждений TypeScript
2. `npm run lint` — без ошибок
3. Открыть каждую страницу в трёх шириных вьюпорта (375/768/1440) — нет горизонтального
   скролла, нет наложения элементов
4. Проверить, что на каждой из 4 посадочных страниц разные `<title>`/`<meta description>`
   (не одинаковые/не пустые)
5. Отправить тестовую заявку через каждую форму сайта — убедиться, что уведомление реально
   пришло в Telegram и/или сохранилось в Sanity
6. Проверить все ссылки меню/футера — не должно быть 404 на предусмотренные разделом «Карта
   страниц» страницы
7. Прогнать Lighthouse (или аналог) — Performance и Accessibility не ниже 90 на десктопе
   для каждой из 4 посадочных страниц
8. Убедиться, что ни один цвет/px в исходниках компонентов не захардкожен напрямую
   (быстрая проверка — grep по `#` в файлах компонентов вне конфигурации токенов)
9. Проверить на сервере: сайт открывается по https (сертификат валиден), http редиректит
   на https, firewall ограничивает лишние порты

Если какой-то пункт не проходит — не помечать фазу завершённой, вернуться и исправить.

## 5. Файлы проекта

- `AGENTS.md` — этот файл, правила и стек
- `DESIGN.md` — визуальные токены, типографика, анти-паттерны
- `SPEC.md` — полная функциональная спецификация: карта страниц, контент по блокам,
  SEO-метаданные, промпты для генерации изображений, фазы разработки, критерии приёмки,
  открытые вопросы
